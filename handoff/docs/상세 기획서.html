PLOVE 상세 기획서

사랑을 실천으로 연습하는 서비스. 이 문서는 구현에 필요한 규칙·수치·연동 명세를 담는다. 화면 동작은 Plove 웹 01-02.dc.html이 기준이고, 미션 내용은 missions.js가 원본이다.

태그 읽는 법

구현됨 프론트에 동작한다 · 서버 필요 화면만 있고 백엔드가 없다 · LLM 모델 호출이 걸린다

1개요와 용어

한 줄 정의

매일 하나씩 현실에서 사랑을 실천하고, 인증과 회고 대화로 검증받아 성장하는 서비스.

3미션 데이터

원본은 missions.js 하나다. window.PLOVE_MISSIONS 전역에 코스 키 → 미션 배열 30개 구조로 들어 있다. 총 180개.

파일 구조

window.PLOVE_MISSIONS = {
  self: [ {…}, {…}, … 30개 ],
  lover: [ … ], family: [ … ],
  friend: [ … ], coworker: [ … ], pet: [ … ]
};

정적 파일로 두고 <script src>로 읽는다. 서버로 옮긴다면 GET /missions 한 번에 전체를 내려받아 캐시하는 방식이 맞다 — 미션은 사용자마다 다르지 않고 자주 바뀌지도 않는다.

토큰 치환

토큰치환 대상규칙
{m}가족 구성원fam: "one"이면 미션 번호로 famMembers를 순환 배분 · "all"이면 "가족"
{p}반려동물이름이 입력된 첫 아이. 없으면 고른 종류명

치환은 제목·목표·과제·기록칸 안내·인증 슬롯 라벨 모두에 적용한다.

30번 미션은 특수하다

모든 코스의 30번은 코스 회고다. 인증·기록을 받지 않고, 29개 미션의 기록을 시간순으로 보여주는 페이지로 열린다.

  • heavy에서 위반 — 배포 중단 다른 지표가 아무리 좋아도 고치기 전엔 내보내지 않는다

이밸이 잡지 못하는 것

자동 검사는 형식 위반만 본다. 아래는 사람이 읽어야 한다.

  • 질문이 진부한지 — 형식은 맞는데 매번 "어떤 기분이었나요?"만 나온다
  • 코멘트가 사용자의 말을 실제로 반영했는지 — 인용은 했지만 맥락이 어긋난다
  • 캐릭터가 구분되는지 — 프시케와 코디가 같은 말투를 쓴다
  • 편지가 감동적인지 — 이건 끝까지 사람의 판단이다

배포 전에 good과 heavy 두 케이스의 응답 전문은 반드시 읽는다.

15이메일 발송 서버 필요

화면에서는 입력과 단계 표시만 한다. 실제 발송은 서버가 맡는다 — 도메인 인증 없이 보내면 스팸으로 분류돼 초대가 전달되지 않는다.

발송이 필요한 지점 2곳

지점화면받는 사람본문에 담길 것
파트너 초대screen: "invite"초대받는 사람 1명초대한 사람 이름, 함께 볼 클래스 목록, 수락 링크, 7일 만료
구독권 선물screen: "gift"선물받는 사람 (여러 명 반복)보낸 사람 이름, 한 달 구독권, 수령 링크, 남긴 메시지

준비물

  • 발송 서비스 — AWS SES, Resend, Postmark 중 하나. 국내 수신율은 SES가 안정적이다
  • 도메인 인증 — SPF, DKIM, DMARC 레코드를 plove.kr에 등록한다. 이게 없으면 Gmail이 스팸으로 보낸다
  • 발신 주소 — no-reply@plove.kr (발송용), support@plove.kr (회신용)
  • 템플릿 — HTML + 텍스트 두 버전. 이미지는 절대 URL로

토큰

링크에 담는 토큰은 추측 불가해야 한다. 초대 링크를 아는 사람이 수락할 수 있으므로 이메일 일치 검사를 함께 둔다 — 링크를 열어도 초대받은 주소로 로그인하지 않으면 수락되지 않는다.

token       128비트 랜덤 (base62 22자)
expires_at  발송 시각 + 7일
target_email 초대·선물 대상 주소 (수락 시 로그인 계정과 대조)
status      pending | accepted | expired | revoked

서버 동작

  1. 클라이언트가 POST /partner/invite 또는 POST /gift/send를 호출한다 (주소 + 공개 클래스 또는 메시지)
  2. 서버가 결제 여부를 확인한다 — 미결제면 400. 결제 전 초대는 막는다
  3. 토큰을 만들고 invites / gifts 행을 pending으로 쓴다
  4. 발송 큐에 넣는다. 동기 발송하지 않는다 — 발송 서비스 지연이 응답 시간에 묻히면 사용자가 두 번 누른다
  5. 클라이언트에는 { ok: true, sent_at }만 즉시 돌려준다
  6. 워커가 큐를 소비해 발송하고 결과를 기록한다

재발송과 주소 변경

  • 수락 전에는 주소를 바꿔 다시 보낼 수 있다 — 기존 토큰을 revoked로 바꾸고 새로 만든다. 이전 링크가 살아 있으면 먼저 받은 사람이 수락해버린다
  • 재발송은 60초에 한 번으로 제한한다 (같은 주소 기준)
  • 하루 발송 상한 — 초대 10건, 선물 30건. 넘으면 429

수락 흐름

  1. 받는 사람이 링크를 연다 → GET /invite/:token으로 상태를 확인한다
  2. 만료·철회·이미 수락이면 각각 다른 안내 화면을 보여준다
  3. 구글 로그인을 거친다 → 로그인 계정 주소가 target_email과 같아야 수락 가능
  4. 다르면 "이 초대는 na***@gmail.com으로 보내진 초대예요"로 막는다 (전체 주소는 가리고 보여준다)

  • 잠긴 노드는 회색 판 + 흑백 아이콘 + 자물쇠
  • 번호는 아이콘 아래 알약 배지

19개발 우선순위

1차 — 이게 없으면 서비스가 아니다

  1. Google OAuth + 진행 상태 저장 — 지금은 새로고침하면 전부 사라진다
  2. 파일 업로드 스토리지 — 인증물이 URL.createObjectURL이라 휘발된다
  3. LLM 연동 — 회고 질문과 채점. 나머지 둘은 빈도가 낮다
  4. 배포 — 공개 URL이 없으면 아무도 볼 수 없다

2차 — 수익과 유지

  1. 결제 (구독 빌링키 + 보석 단건)
  2. Vision 인증 분석
  3. 파트너 초대 메일·연결
  4. 회고 공유 링크

3차 — 완성도

  1. 아이콘 41장 적용
  2. LLM 이밸 정기 실행
  3. 팀 구독권 어드민
  4. 푸시 알림
